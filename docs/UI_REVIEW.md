# UI review

- Date: 2026-10-23
- Commit: a38ee84 (of `docs/ui-review/findings.json`)
- Screens: 16
- Screenshots: 101
- Automated groups: 13

A review of every main screen at 1280, 768 and 390 px (light and dark, and German at 390), from the screenshots of `pnpm ui:review` and its layout checks, judged against [DESIGN.md](DESIGN.md) (§3.7 for the phone) and the phone rules C-APP-25, C-APP-35 and C-APP-36. The run of step 41 used a fresh seed: a database migrated and seeded from empty (`pnpm db:migrate`, `pnpm db:seed`), so the screens show only the seed users and *Japan 2026*; its 22 groups are the same as those of the step 40 run on the dev database. Every screenshot was then reviewed on its own, one image per worker context, in [ui-review/notes/](ui-review/notes/) (see *Review notes*). The app scrolls inside its own containers, so the "full page" JPEGs are only as tall as the viewport and show the top of long screens. No finding is `high`: every task can be finished at every width. Phone findings come first in each severity because the phone is the primary device; each row becomes its own step. Step 42 fixed the 29 rows of the sets S-01 to S-08 of [MOBILE_SKETCH.md](MOBILE_SKETCH.md); *Screens* and *Automated findings* now come from its after run, again on a fresh seed (a separate database migrated and seeded from empty), and the step's before run on the base commit is compared with it card by card in the change panel of `pnpm ui:changes`.

## How to repeat

1. Start the stack with `pnpm dev:e2e` against a database migrated and seeded from empty (for example a separate database: `DATABASE_URL=…/tripboard_review pnpm db:migrate`, `pnpm db:seed`, and the same `DATABASE_URL` for `pnpm dev:e2e`; the run only reads), then run `pnpm ui:review`. It writes 101 screenshots, `raw/*.json`, `findings.json` and `summary.md` to `test-results/ui-review/`.
2. Copy the grouped results with `node scripts/ui-review/summarize.mjs --docs` into `docs/ui-review/findings.json`, then copy the screenshots cited in *Findings* from `test-results/ui-review/` into `docs/ui-review/` (JPEG, at most 300 kB each; keep no file that no row cites).
3. Update the *Screens* counts and add or change a row in *Automated findings* for every group key of the new `findings.json`, and add rows to *Findings* for what the screenshots show that a machine cannot measure. `pnpm test` runs the check and names what is wrong.
5. Review every screenshot on its own: `node scripts/ui-review/queue.mjs` prints the 101 images in review order and writes a stub note for each in `docs/ui-review/notes/`. Give one worker at a time [notes/_BRIEF.md](ui-review/notes/_BRIEF.md) with `{{image}}` replaced by one image name, wait for its note, check it with `node scripts/ui-review/notes.mjs --note <image>` (send failures back at most twice), then `/clear` the worker before its next image; run at most 4 workers.
6. Merge: compare the notes of each screen across widths, themes and locales and the same parts across screens, turn every `new` into the `U-` row it becomes (one row per problem, citing the notes and a screenshot) or into `rejected: <reason>`, and update *Review notes*. `node scripts/ui-review/notes.mjs` checks all notes against this report.
7. For a step that fixes rows: copy the output of `pnpm ui:review` on the base commit (fresh seed) to `test-results/ui-review-before/` before the first app change, write the manifest `docs/ui-review/changes-NN.json` while fixing, repeat the run into `test-results/ui-review/` at the end, then `pnpm ui:changes` builds the change panel `test-results/ui-changes/index.html` with each fix's before and after screenshots, where the owner marks every card *Accepted* or *Needs work* and exports the verdicts.
4. When a step takes a row, write `step NN` in its *Step* cell; when the step is done, write `fixed in step NN`. Rows are never deleted, and the *Finding* cell of an automated row keeps naming the `U-` ID.
