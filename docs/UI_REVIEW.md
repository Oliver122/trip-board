A review of every main screen at 1280, 768 and 390 px (light and dark, and German at 390), from the screenshots of `pnpm ui:review` and its layout checks, judged against [DESIGN.md](DESIGN.md) (§3.7 for the phone) and the phone rules C-APP-25, C-APP-35 and C-APP-36. The run used a local dev database, not a fresh seed: a real user is a member of *Japan 2026*, there are open invites, and *My trips* lists many trips left by e2e runs. The data itself is not reported; only how the UI copes with it is. The app scrolls inside its own containers, so the "full page" JPEGs are only as tall as the viewport and show the top of long screens. No finding is `high`: every task can be finished at every width. Phone findings come first in each severity because the phone is the primary device; nothing here is fixed yet, each row becomes its own step.

## How to repeat

1. Start the stack with `pnpm dev:e2e` against a migrated and seeded database (the run only reads), then run `pnpm ui:review`. It writes 101 screenshots, `raw/*.json`, `findings.json` and `summary.md` to `test-results/ui-review/`.
2. Copy the grouped results with `node scripts/ui-review/summarize.mjs --docs` into `docs/ui-review/findings.json`, then copy the screenshots cited in *Findings* from `test-results/ui-review/` into `docs/ui-review/` (JPEG, at most 300 kB each; keep no file that no row cites).
3. Update the *Screens* counts and add or change a row in *Automated findings* for every group key of the new `findings.json`, and add rows to *Findings* for what the screenshots show that a machine cannot measure. `pnpm test` runs the check and names what is wrong.
4. When a step takes a row, write `step NN` in its *Step* cell; when the step is done, write `fixed in step NN`. Rows are never deleted, and the *Finding* cell of an automated row keeps naming the `U-` ID.
