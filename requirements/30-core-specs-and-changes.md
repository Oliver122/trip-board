# Step 30 — Core specs, change steps and a generated requirements index

**Goal:** anyone can read how a feature works *today* in one core file per area, see which step changed it and which tests prove it, and `pnpm req:build` writes one aggregated index that CI keeps honest.
**Depends on:** 21, 29

## Scope
- In: `requirements/core/<area>.md` files backfilled from the current behavior of steps 00–29; a “Core changes” section in every step file from now on (a step becomes a *change* to the core); an “integrate” stage at the end of a step that applies its core changes; `pnpm req:build` that parses core and step files and writes `requirements/INDEX.md`; `pnpm req:check` in CI; updated `/req-new`, `/req-implement` and `/req-test-report` commands; README conventions rewritten for the new flow; steps 24 and 25 added to the README graph and table.
- Out: changing any app behavior, tests or routes (the backfill describes, it does not fix; gaps found go into the “Known gaps” list for a later step); moving or renaming existing step files (they stay as history at `requirements/NN-slug.md`); rewriting old step files beyond the one added header line (R-30-05); a web UI for requirements.

## Decisions
| Topic | Decision |
| --- | --- |
| Areas | `app` (shell, design, i18n, responsive, a11y), `auth`, `trips`, `map`, `spots`, `kinds`, `images`, `list` (search, filter, sort), `planning`, `home`, `members`, `export`, `discussions`, `import`, `live`, `admin`, `ops` (tooling, CI/CD, local dev). One file each: `requirements/core/<area>.md` |
| Core IDs | `C-<AREA>-NN`, area code fixed per file (`APP`, `AUTH`, `TRIP`, `MAP`, `SPOT`, `KIND`, `IMG`, `LIST`, `PLAN`, `HOME`, `MEMB`, `EXP`, `DISC`, `IMP`, `LIVE`, `ADMIN`, `OPS`). IDs are never reused or renumbered; a removed rule keeps its row with status `removed` |
| Core row | `\| ID \| Rule \| Status \| Since \| Changed by \| Tests \|`. *Rule* is the current behavior in one or two sentences, as concrete as an R-row. *Status* is `active` or `removed`. *Since* is the step that added it, *Changed by* the later steps that changed it, *Tests* the T-IDs that prove the current rule |
| Step = change | Step files keep `R-NN-xx` / `T-NN-xx`. New section `## Core changes` (after Requirements): `\| Core ID \| Change \| From \|` with Change `add`, `modify` or `remove` and From the R-IDs that cause it. A new core ID in an `add` row is reserved by writing it in the step |
| Integrate | After the DoD passes, the step's core changes are applied to the core files and the step gets `**Status:** integrated YYYY-MM-DD`. Until then the core files describe the state *before* the step |
| Test location | A T-ID is “located” if its exact ID appears in a file under `apps/`, `packages/`, `e2e/` or `scripts/` (as today). `manual` and `ci` tests are located by their latest report instead |
| Index | `requirements/INDEX.md` is generated, committed, and starts with “Generated by `pnpm req:build` — do not edit” |

## Requirements

### Core files
| ID | Requirement |
| --- | --- |
| R-30-01 | `requirements/core/` holds the 17 area files from the Decisions table. Each starts with `# Core — <Area>`, one paragraph saying what the area covers and which areas it touches, then one rule table in the documented column order. Optional `##` sub-headings group rows; every table in the file uses the same columns |
| R-30-02 | Backfill: every R-row of steps 00–29 is either (a) folded into at least one core rule, listed in that rule's *Since* or *Changed by*, or (b) listed in `requirements/core/_unmapped.md` with a one-line reason (e.g. “one-off migration”, “superseded by R-28-13”, “tooling only, see C-OPS-04”). Where a later step overrides an earlier one (e.g. R-07 kind checkboxes → R-28 → R-29 chips), the core rule states only the current behavior |
| R-30-03 | Every `active` core rule lists at least one T-ID in *Tests*, taken from the steps that built or changed it. A rule whose behavior has no test is still written down, with `—` in *Tests*, and is listed under “Known gaps” at the end of its area file |
| R-30-04 | While writing a rule, if the code and the step text disagree, the core rule describes what the code does today and the disagreement goes into “Known gaps” with the step R-ID and the file that differs. No app code is changed in this step |
| R-30-05 | Each existing step file 00–29 gets one line under **Depends on**: `**Core:** C-SPOT-03, C-KIND-01, …` (the core IDs it added or changed, from the backfill) and `**Status:** integrated 2026-10-11`. Nothing else in old step files changes |

### Change flow
| ID | Requirement |
| --- | --- |
| R-30-06 | `README.md` “Conventions” describes the flow in this order: core files are the truth for current behavior → a new step is a change with R/T rows and a `## Core changes` table → `/req-implement` builds it → the DoD passes → integrate (apply core changes, set status, `pnpm req:build`) → `/req-test-report`. It shows a filled example of a `## Core changes` table and of a core rule row before and after a `modify` |
| R-30-07 | `.claude/commands/req-new.md` adds the `## Core changes` section to the template, tells the author to read the affected core files first instead of old steps, and requires every R-row to appear in *From* of at least one core change row (or be marked `(no core change)` with a reason, e.g. pure test hardening). New core IDs take the next free number in their area |
| R-30-08 | `.claude/commands/req-implement.md` gets a final “Integrate” stage that runs only when all DoD tests pass: apply each `add`/`modify`/`remove` to the core files (rule text, *Changed by*, *Tests*, status), add the step's `**Status:** integrated <date>` line, run `pnpm req:build`, and include the core diff in its summary. If the DoD fails, core files are not touched |
| R-30-09 | `.claude/commands/req-test-report.md` adds a “Core” line to the report: the core IDs the step changes and whether `pnpm req:check` passes |

### Aggregated index
| ID | Requirement |
| --- | --- |
| R-30-10 | `pnpm req:build` (`scripts/req/build.mjs`, Node, no new runtime dependency) parses `requirements/core/*.md` and `requirements/NN-*.md` and writes `requirements/INDEX.md` with: (1) the step graph as mermaid, built from each step's **Depends on** (the step numbers only, ignoring text in brackets); (2) the steps table (number, linked title, status, core IDs, “Result you can check” taken from a `**Result:**` line in each step); (3) per area, every core rule: ID, short rule (first sentence), status, since, changed by, tests, and the file(s) each test is located in; (4) a coverage summary: rules per area, rules without tests, T-IDs not located |
| R-30-11 | The output is deterministic: running `req:build` twice, or on another machine, gives a byte-identical `INDEX.md` (sorted by step number, then core ID; no timestamps; paths repo-relative with `/`). It passes `prettier --check` |
| R-30-12 | `README.md` keeps its intro, conventions, test types, test doubles, seed data and global DoD; its hand-written graph and steps table are replaced by a link to `INDEX.md`. The “23 small steps” text is fixed. Each step file 00–29 gets the `**Result:**` line with the text from today's README table (24 and 25 get new ones) |
| R-30-13 | `pnpm req:check` (same script, `--check`) exits non-zero with one line per problem when: `INDEX.md` differs from a fresh build; a core ID is duplicated, malformed or in the wrong area file; a step's `## Core changes` names a core ID that does not exist (for `modify`/`remove`) or already exists (for `add` in a step that is not integrated); an `integrated` step has core changes that are not reflected in *Since*/*Changed by*; a T-ID in a core row does not exist in any step's DoD; an `active` rule has `—` in *Tests* but is not in its area's “Known gaps”; a non-`manual`/`ci` T-ID in a core row is not located in any test file |
| R-30-14 | CI runs `pnpm req:check` in the `static` job next to `pnpm lint`, so a pull request that edits a core or step file without regenerating `INDEX.md`, or that breaks a rule above, fails `ci-passed` |
| R-30-15 | The T-IDs that are not located today (393 − 316) are either tagged in the test that covers them (a comment `// T-NN-xx` or the ID in the test title) or, if no such test exists, their core rules go to “Known gaps”. After this step `pnpm req:check` passes on `main` |
