# Requirements — iterative build plan

The site is built in small steps. Each step ships something that works, can be checked on its own, and is finished only when its **Definition of Done (DoD)** passes. Each DoD is a list of test requirements.

Sources: [`docs/PROJECT_SCOPE.md`](../docs/PROJECT_SCOPE.md) (what), [`docs/DESIGN.md`](../docs/DESIGN.md) (how it looks), [`docs/database/DATABASE.md`](../docs/database/DATABASE.md) (data), [`docs/STITCH_DESIGN_GUIDE.md`](../docs/STITCH_DESIGN_GUIDE.md) (visual prompt).

---

## Steps and current behavior

- **How a feature works today:** one core file per area in [`core/`](./core/), e.g. [`core/kinds.md`](./core/kinds.md). Each rule lists the step that added it, the steps that changed it and the tests that prove it.
- **Step graph, steps table, every rule with its test files, coverage:** [`INDEX.md`](./INDEX.md). It is generated by `pnpm req:build`; never edit it by hand. `pnpm req:check` (also run in CI) fails when it is stale or a core file breaks the rules below.
- **History:** the step files `NN-slug.md` stay as they were written. From step 30 on, a step is a *change* to the core files.

Steps on parallel branches of the graph can be built in any order; the **Depends on** line of each step is the only ordering rule.

---

## Conventions

**Flow of a change**
1. **Core files are the truth for current behavior.** Read `requirements/core/<area>.md` first, not old steps.
2. **A new step is a change.** `/req-new` writes `requirements/NN-slug.md` with `R-` rows, `T-` rows and a `## Core changes` table saying which core rules it adds, modifies or removes.
3. **`/req-implement NN` builds it.**
4. **The DoD passes.** Until then the core files still describe the state *before* the step.
5. **Integrate:** apply the core changes to the core files, set `**Status:** integrated YYYY-MM-DD` and the `**Core:**` line in the step, run `pnpm req:build` and `pnpm req:check`.
6. **Stack and PR:** every part of a run (step or `+` task) is committed as atomic, individually green commits on its own branch and opened as its own pull request, based on the previous part's branch (stacked PRs). The head agent pushes only green parts and never merges. `pnpm req:stack` plans branches and bases.
7. **`/req-test-report NN`** writes `requirements/reports/NN-report.md`.

Step header, under the title:
```
**Goal:** ...
**Depends on:** 07, 13
**Result:** what you can check by hand
**Core:** C-KIND-04, C-KIND-12
**Status:** planned
```
`**Status:**` is `planned` or `integrated YYYY-MM-DD`.

Example `## Core changes` table (after Requirements, before the DoD). `From` lists the `R-` rows that cause the change; a rule that is not touched by a requirement (pure test hardening) is marked `(no core change)` in its R-row instead:
```
## Core changes
| Core ID | Change | From |
| --- | --- | --- |
| C-KIND-12 | add | R-31-01 |
| C-KIND-04 | modify | R-31-02, R-31-03 |
| C-KIND-07 | remove | R-31-04 |
```

A core rule row before and after `C-KIND-04 | modify` by step 31 (the new text, step number in *Changed by*, tests of the new behavior; *Since* never changes, a removed rule keeps its row with status `removed`):
```
| C-KIND-04 | A kind name is 1-24 characters. <!-- R-28-05 --> | active | 28 | — | T-28-05 |
| C-KIND-04 | A kind name is 1-40 characters. <!-- R-28-05, R-31-02 --> | active | 28 | 31 | T-28-05, T-31-02 |
```

**IDs**
- `R-<step>-<n>`: a requirement, e.g. `R-07-03`.
- `T-<step>-<n>`: a test requirement in the DoD, e.g. `T-07-05`. Each test lists the requirement(s) it covers. A test is *located* when its exact ID appears in a file under `apps/`, `packages/`, `e2e/` or `scripts/` (a `// T-07-05` comment or the ID in the test title); `manual` and `ci` tests are located by the step's report instead.
- `C-<AREA>-NN`: a core rule, e.g. `C-KIND-04`. The area code is fixed per file (`APP`, `AUTH`, `TRIP`, `MAP`, `SPOT`, `KIND`, `IMG`, `LIST`, `PLAN`, `HOME`, `MEMB`, `EXP`, `DISC`, `IMP`, `LIVE`, `ADMIN`, `OPS`). IDs are never reused or renumbered. Full file contract: [`core/_FORMAT.md`](./core/_FORMAT.md).

**Test types**

| Tag | Tool | Runs against |
| --- | --- | --- |
| `unit` | Vitest | pure functions, React components (Testing Library) |
| `api` | Vitest + Fastify `inject` | real Postgres 16 (Testcontainers or the CI service), no network |
| `db` | `psql` / Vitest | migrated database |
| `e2e` | Playwright (Chromium; WebKit from step 15) | full stack with seeded data |
| `a11y` | `@axe-core/playwright` | rendered pages |
| `ci` | GitHub Actions run | a throwaway pull request or a merge to `main` |
| `manual` | person + checklist | only where automation is not worth it (e.g. real Discord login) |

**Test doubles**
- **Discord:** a fake OAuth server in tests. Plus `POST /test/login {discordId}` that only exists when `NODE_ENV=test` and creates a session directly.
- **Nominatim:** recorded responses (fixtures); the API never calls the real service in tests.
- **Blob storage:** MinIO container in `api`/`e2e` tests.
- **Time:** injectable clock for invite expiry and sessions.

**Seed data** — `pnpm db:seed` creates:
- Users `sven` (owner, platform admin), `aiko` (planner), `tom` (visitor).
- Trip *Japan 2026* with 6 spots, 2 buckets, 1 single entry, 2 home spots.
- 90 days of `activity_events` and `metrics_daily` rows, so admin graphs have data.

E2E tests use this seed.

## Global Definition of Done (applies to every step)

| ID | Check |
| --- | --- |
| G-1 | All step tests (`T-xx-*`) pass in CI |
| G-2 | `pnpm lint`, `pnpm typecheck`, `pnpm test` pass with zero errors |
| G-3 | Every new route has `api` tests for: success, validation error (400), unauthenticated (401), wrong role (403), not found / other trip (404) |
| G-4 | No hard-coded UI strings: every visible text comes from `en` **and** `de` translation files (lint rule + missing-key test) |
| G-5 | New UI passes axe with no serious/critical issues |
| G-6 | New UI checked at 1280 px and 768 px (Playwright screenshots attached to PR) |
| G-7 | Loading, empty and error states exist for every new data view |
| G-8 | README / docs updated if setup, env vars or behavior changed |
| G-9 | Database changes come with a migration; `docs/database/checks.sql` still passes |
| G-10 | From step 04 on, every write a user makes records an `activity_events` row in the same transaction (action names from `docs/database/DATABASE.md` §3), covered by at least one `api` test per action |
